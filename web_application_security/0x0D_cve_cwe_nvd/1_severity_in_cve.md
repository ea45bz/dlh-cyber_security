## How does the severity of CVEs affect an organization’s prioritization of security measures?

| **Severity**         | **Typical CVSS Base Score Range** | **What It Means to You**                                                                                              | **Practical Response Strategy**                                                                                                                                                                                                                                                                                       |
| -------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Critical (≥ 9.0)** | 9‑10                              | Exploit can lead to full system compromise, data exfiltration or loss of availability with _no_ mitigations in place. | • Patch **within 24 hrs** (or as soon as a hot‑fix is released).<br>• Deploy the fix in a **staging environment first**, run regression & security tests.<br>• Rollout on all affected assets immediately.<br>• Trigger incident‑response playbook: alert SOC, log detailed activity, run post‑exploitation analysis. |
| **High (7.0–8.9)**   | 7‑8.9                             | Likely to give attackers significant privilege or data access; usually exploitable in the wild.                       | • Patch within **72 hrs** if a public patch exists.<br>• If no patch is available, implement a _mitigation_ (e.g., firewall rule, WAF rule).<br>• Add monitoring for anomalous activity (failed logins, unusual API calls).                                                                                           |
| **Medium (4.0–6.9)** | 4‑6.9                             | Exploit may require some skill or access but can still damage systems or data.                                        | • Prioritize based on asset criticality: patch assets that handle sensitive data first.<br>• Schedule in the next planned maintenance window if no high exposure.<br>• Review configuration changes that reduce attack surface (e.g., disable unnecessary services).                                                  |
| **Low (< 4.0)**      | < 4                               | Minor impact or very low exploitability.                                                                              | • Include in routine scanning reports; may be patched during standard patch‑cycle.<br>• If the affected asset is highly critical (e.g., exposed web API), consider a quicker patch even for low severity.<br>• Document and track to maintain a complete audit trail.                                                 |

## Provide examples of how different severity levels (low, medium, high, critical) influence response strategies.

| Scenario                                                                                             | CVE Severity   | Response                                                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A **High** CVE (CVE‑2024‑1010) in the _public‑facing web API_ that could allow SQL injection.        | High (7.8)     | 1️⃣ Deploy hot‑fix to all production instances within 48 hrs.<br>2️⃣ Add an WAF rule blocking suspicious payloads during deployment.<br>3️⃣ Run automated functional and security tests in staging.<br>4️⃣ Update incident‑response playbook, notify SOC.                |
| A **Low** CVE (CVE‑2024‑2020) in a legacy library used only on the dev environment.                  | Low (2.5)      | 1️⃣ Schedule patch for next weekly maintenance window. <br>2️⃣ Verify that the library isn’t accidentally included in production builds.                                                                                                                               |
| A **Critical** CVE (CVE‑2024‑3030) in an internal authentication service with no public exploit yet. | Critical (9.3) | 1️⃣ Apply the vendor patch immediately. <br>2️⃣ Block all inbound traffic to the service except for required management IPs until the fix is verified.<br>3️⃣ Run a security scan on the service post‑patch and perform a brief penetration test to confirm mitigation. |

### Putting It Into Practice

1. **Automate triage** – Use your vulnerability scanner or CVE feed to assign severity → ticket priority automatically.
2. **Use a risk matrix** – Combine CVSS score with asset criticality & exposure to decide on _how soon_ to act.
3. **Document “why”** – In the ticket, note why an unexpected high‑severity CVE might be deferred (e.g., no active exploit or low exposure) so the decision is transparent.
4. **Measure outcomes** – Track MTTR by severity; a healthy posture shows that criticals are patched fastest and lows move to “closed” with minimal delay.
