# 1 Comparison table of the 6 encryption levels from Sec+ 1.4:

| Level         | Scope                            | Performance Impact                                                                                                         | Key Management                                                              | Use Case                                                                                                                             |
| ------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Full‑disk** | Entire physical or virtual disk  | High decryption cost on _every_ I/O operation, but negligible per‑file overhead; mitigated by AES hardware acceleration    | One master key per host (stored in TPM/HSM) – a single rotate point         | When you want blanket protection for all disk contents and do not need selective access (e.g., general‑purpose servers or desktops). |
| **Partition** | One logical partition            | Similar to full‑disk, but only that partition is encrypted; OS can stay unencrypted                                        | One key per partition – stored in HSM or device‐level key store             | When you need to isolate a data set (e.g., a database) from non‑sensitive partitions.                                                |
| **Volume**    | Logical volume (may span disks)  | Overhead of the underlying LVM metadata; encryption per block is essentially full‑disk performance if hardware‑accelerated | One key per volume – managed by storage controller or HSM                   | When you want flexible disk aggregation with consistent key management across multiple physical drives.                              |
| **File**      | Individual files                 | Encryption/decryption is performed only for selected files; no impact on other data                                        | Key per user/group or per file – stored in user keyring/HSM                 | When you need selective protection of a subset of files without touching the rest.                                                   |
| **Database**  | Entire DB instance or tablespace | Minor I/O overhead (~1‑3 %) because every query must decrypt rows                                                          | One key per database cluster – stored in the DBMS key store or an HSM       | When you want all data protected transparently to applications, with minimal schema changes.                                         |
| **Record**    | Individual fields or records     | Highest overhead—encryption/decryption happens on a per‑row basis; may affect query performance                            | Key per field or per application – usually managed in an external key vault | When you must enforce least‑privilege data access and protect only the most sensitive attributes.                                    |

# 2 MedDefense Encryption‑Level Map

| Data Store                                     | Recommended Level                                                                          | Why this is best for MedDefense                                                                                                                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Patient records – PostgreSQL (ehr-db-01)**   | **Database** (TDE) with optional _record_ encryption on SSN / credit cards                 | The entire database contains PHI that must be readable by clinical staff, so a transparent layer keeps performance acceptable while protecting all tables; sensitive columns can be encrypted if query patterns permit. |
| **Backup data – NAS‑01**                       | **Volume** (Synology “Encrypted Shared Folder”)                                            | The NAS stores large backups from many sources; encrypting at the volume level protects everything on that shared folder, is easy to manage across multiple disks, and imposes only a small I/O overhead (~5 %).        |
| **Financial records – MySQL (billing‑srv-01)** | **Database** with _column_ encryption for SSN / credit card fields                         | The database holds billing data that must be searchable; TDE protects the whole tablespace while column‑level encryption safeguards the most regulated values.                                                          |
| **Medical images – PACS (pacs-srv-01)**        | **File** level (encrypt each DICOM folder)                                                 | Images are large files; encrypting at the file level allows selective protection of only those folders that contain PHI and keeps read/write overhead low compared to full‑disk encryption.                             |
| **Email data – O365**                          | **None (cloud‑managed)**                                                                   | Microsoft already applies AES‑256 + per‑mailbox keys; adding another layer is unnecessary and would duplicate effort.                                                                                                   |
| **Employee laptops**                           | **Full‑disk** (BitLocker/FileVault) with TPM key store                                     | The laptop contains OS, application data, and PHI on the workstation—full‑disk encryption protects all content if the device is lost or stolen.                                                                         |
| **BD Alaris pump firmware / configuration**    | **File/Record** (firmware image signed + encrypted; device‑specific key in secure element) | Firmware is a small binary that should be cryptographically protected from tampering; encrypting the image and storing its key in a hardware security module prevents unauthorized updates.                             |
